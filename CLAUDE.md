# SQL Playbook — notes for Claude

SQL practice site: exercises on real sample databases, often with several solutions compared side by side, each with a
MySQL version. PostgreSQL 18 runs in the browser (PGlite); MySQL 8.4 versions are verified ahead of time.
Repo: https://github.com/Kirill-2112/sql-playbook (public). The owner writes in Russian; the site content is in English.

## Golden rule

Nothing is published unless `npm run verify` passes: every PostgreSQL solution returns the same rows as solution A,
every MySQL solution returns the same rows as PostgreSQL, and each exercise has at least one solution verified on MySQL.
GitHub Actions (`.github/workflows/verify.yml`) runs the whole pipeline on every push.

## Layout

- `scripts/build-datasets.ts` — official source → MySQL → `public/datasets/<id>.pg.sql` + `datasets/build/<id>.mysql.sql`
  + `src/content/datasets/<id>.schema.json`, then compares both builds row by row. Output must be byte-for-byte reproducible.
- `scripts/sources/*.ts` — converters/samplers for sources that are not plain MySQL (Northwind, Employees, AdventureWorks,
  Airlines). `pgTypes` in a dataset config gives a column a PostgreSQL-only type (timestamptz, interval, boolean, integer[]).
- `scripts/verify.ts` — checks every exercise on PGlite and the local MySQL; writes `src/content/generated/verification.json`.
- `src/content/exercises/<dataset>.ts` — exercises (`Exercise` type in `src/content/types.ts`). Script exercises (DDL/DML,
  functions, triggers) set `checkSql` (and `checkSqlMysql` if needed); PG runs them in a rolled-back transaction, MySQL on a
  throwaway copy (`pb_scratch`).
  `setupSql` (+ `setupSqlMysql`) runs before the learner's SQL, e.g. to create a messy staging table; `files` attaches
  CSVs that `COPY … FROM 'name.csv'` (PG, pointed at PGlite's /dev/blob) or `LOAD DATA LOCAL INFILE 'name.csv'` (MySQL,
  served from memory; verify turns on local_infile) read. Learners' BEGIN/COMMIT/ROLLBACK become savepoints of the
  sandbox transaction (`src/utils/emulateTransactions.ts`), so transaction exercises use real BEGIN … COMMIT in PG too.
  Anything that writes (create, grant, insert, copy…) must have a `checkSql`: only then MySQL runs on the throwaway copy.
  MySQL users/roles are server-wide: verify and build:reference drop every account a run created. Use orderMatters
  false for privilege lists (information_schema sorts names in its own collation).
  Never run two `verify` processes at once: they share `pb_scratch` and break each other ("Unknown database 'pb_scratch'").
  A full run of ~1,060 exercises takes 40–60 minutes; run it in the background with a long timeout.
- `src/content/reference/<group>.ts` — the functions & keywords reference (`ReferenceEntry` in types.ts). Every entry
  has an example; `npm run build:reference` runs it on PGlite and MySQL (database `pb_reference`) and writes
  `generated/reference.json` (results + exercises found by the entry's `match` regex). `example.mysql`: omitted = same
  text, null = no MySQL version. Examples with their own BEGIN/COMMIT run statement by statement on a fresh PGlite.
  MySQL `->`/`->>` work only on columns; use json_extract/json_unquote on expressions. Run `-- --links` after adding docs.
- The learning app: `/` is the path (`LearnPage`), `/learn/:lessonId` a full-screen lesson, `/progress` stats; the old
  home is `/overview`. `npm run build:lessons` (scripts/build-lessons.ts) builds `generated/lessons.json` from the
  exercises: levels 1–2, one skill per topic, 3 lessons per skill (gap, rows, "find the bug" or "put the lines in order",
  gap, then "write the query"). "Find the bug" reuses a verified wrong gap variant; "order" uses clause-per-line solutions. Every wrong gap option is run on PGlite and kept only if it changes the result or fails. Deterministic;
  CI checks it is current, so rerun it after changing exercises. Progress lives in localStorage (`src/progress/store.ts`).
- `src/content/topics.ts` — the 58-topic curriculum (5 levels). `src/content/datasets.ts` — dataset metadata and attribution.
- UI: React + TypeScript strict + styled-components; one component per file in `src/components/`; colours/spacing only from
  `src/theme/tokens.ts`.

## Writing exercises — lessons learned

- Make answers deterministic: full tie-breakers in ORDER BY; avoid ordering by text that differs by collation
  (PGlite uses C collation, MySQL utf8mb4_0900_ai_ci: "USA" vs "United Kingdom", accents, case).
  Equality, joins and COUNT(DISTINCT) on text follow the collation too ("Historia" = "História" in MySQL):
  add COLLATE utf8mb4_bin on the MySQL side when PostgreSQL compares exactly.
- PG sorts NULLs last, MySQL first; MySQL ORDER BY on ENUM uses definition order.
- Always ROUND averages and ratios (PG numeric vs MySQL decimal precision). Use `100.0 *` to avoid integer division in PG.
- Avoid MySQL reserved words as aliases/columns: change, lines, empty, rank, group, rows, key, order…
- MySQL: no FILTER, FULL JOIN, MERGE, RETURNING, DISTINCT ON, generate_series, ::, partial indexes, bool_and;
  `||` is OR; `/` is decimal (use DIV); temp tables can't be referenced twice in one query.
- When a learner-visible claim mentions a number (counts, percentages), check it against the data first.
- PG generated columns accept only IMMUTABLE expressions: concat_ws, to_char, timestamptz::date and age(date, date) are refused (age(d1::timestamp, d2::timestamp) works); || with
  coalesce, extract, date − date and integer arithmetic are fine. Day-of-year tricks (MAKEDATE(y, 182)) break in leap years.
- MySQL collations: strings made by CAST/JSON_TABLE get the connection collation (utf8mb4_general_ci via mysql2), not the
  table's utf8mb4_0900_ai_ci; comparing them fails with "Illegal mix of collations". Add COLLATE utf8mb4_0900_ai_ci.
- Upstream files can change under the same URL (Postgres Pro re-published the Airlines dump on 2026-10-17, fixing
  "Aerobus" → "Airbus"). CI then fails at the checksum step. Diff old vs new (schema + sorted rows per table), and if the
  change is harmless, update the SHA-256 in the workflow and rebuild.
- Airlines times: timestamptz in PG (the .pg.sql sets `timezone = 'UTC'`, otherwise PGlite uses the computer's zone),
  DATETIME holding UTC in MySQL; compareRows treats "…+00" and the bare value as equal. Local time: AT TIME ZONE vs
  CONVERT_TZ (needs MySQL tz tables, present in the official image). Express durations that may exceed a day as minutes:
  PG prints intervals as "1 day 02:00:00", MySQL TIME as "26:00:00".
